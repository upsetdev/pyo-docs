---
title: Updating Pyo
description: Install new releases from the dashboard, by hand or on a schedule.
---

An installation admin updates Pyo under **Settings → Updates**. Your services keep running while it updates.

## Check for updates

Pyo checks for a new stable release every 6 hours. It asks `api.pyo.dev`, which answers with the latest release from GitHub. If that fails or is slow, Pyo asks GitHub directly. The **Version** panel shows the version that's running, the latest release and when Pyo last checked. Choose **Check now** to look straight away.

When a new release is out, admins see a dot on **Settings** and on **Updates**.

Pyo only uses a release whose `release.json` is signed by Pyo's own release workflow (a [Sigstore](https://www.sigstore.dev) signature). If the signature is missing or doesn't match, the check fails and nothing is installed. A mirror set with `PYO_UPDATE_SOURCE` has to serve the release's signature too.

To stop checking, turn off **Look for new releases**. On a server that can't reach GitHub, set `PYO_UPDATE_CHECK=off`, or point `PYO_UPDATE_SOURCE` at a mirror. See the [system reference](/docs/system-reference#updates).

## Usage counts

With each check, Pyo sends a random install ID and its version, so we can count how many installs run and which versions they're on. The ID is made once and says nothing about your servers. Nothing else is sent, like names, domains, addresses or who you are, and the source IP isn't stored. Each install's daily records are deleted after 90 days.

To stop sending the ID, turn off **Send anonymous usage counts**. Pyo keeps checking for updates. Turning it on again starts a new ID. `PYO_UPDATE_CHECK=off` stops both.

A fresh install made with `PYO_TELEMETRY=off` starts with usage counts off. See [Install count](/docs/install#install-count).

## Update now

[Back up Pyo itself](/docs/backups#backing-up-pyo-itself) first. Database changes can't be undone by going back a version.

Choose **Update now** to see the release before it starts:

- **Before you update:** anything you need to know first, if the release has it.
- **What changes:** Pyo itself, each cluster's agent, your builders, any database changes and the platform services.
- When Pyo's own data was last backed up, with a link to **Settings → Backups**.
- The release notes.

Then confirm the update.

## What happens

1. Pyo moves to the new version one replica at a time, so the dashboard stays up.
2. Then every cluster with an older agent updates on its own. Each agent first checks that it can pull and start the new version, then switches to it.

Your services keep running the whole time. If Pyo's update fails, the old version keeps running.

The result shows in **Activity** and under **Recent updates**. An update is partial when some agents didn't move.

## Agents on other clusters

Pyo updates every cluster's agent for you. There's no button per cluster.

- **An agent that doesn't come back:** if it isn't on the new version within 10 minutes, it's marked failed.
- **An offline agent:** it's skipped, and catches up on the next update.
- **A cluster that needs a refresh:** some updates need a command on each cluster. Until you run it, the cluster shows **Update needed**. See [Refresh a cluster after an update](#refresh-a-cluster-after-an-update).

When some agents are behind, **Settings → Updates** shows **Some agents aren't on** the new version, with **Update now**. This updates only the agents. With automatic updates, it also happens in the maintenance window.

## Refresh a cluster after an update

Most updates need nothing from you. Within a minute of the update, each cluster brings its own install in line with the new Pyo, the agent's permissions included.

Some cases need a command on a cluster:

- **The update to 0.51.0, once.** Before 0.51.0, an agent couldn't update its own permissions. So after this update, each cluster waits for the command once. After that, the agent keeps its permissions current by itself.
- **A release that brings something the agent can't add by itself**, like a new set of permissions or a new Envoy Gateway chart, as in 0.52.0. The release notes then say "After updating, run the connect command shown in each cluster's settings."
- **A cluster that doesn't refresh on its own.** That's a cluster connected with [`PYO_AGENT_SELF_UPDATE=false`](/docs/system-reference#connections). It waits for the command after every update that changes its install.

The cluster Pyo runs on never waits for you. Its server runs the command by itself within a few minutes of the update, 0.51.0 included. So if that's your only cluster, there's nothing to run.

A cluster that waits shows **Update needed** in its **Settings** tab. Run the command under **Refresh this cluster** on the cluster's first server. See [Refresh a cluster](/docs/clusters#refresh-a-cluster).

Your services keep running while a cluster waits. Features that came with the update may stay off on that cluster, and its databases stay on their old images.

On Pyo Cloud, we update Pyo and you never do. Your clusters don't refresh on their own, so the command is yours to run after each update. See [Agent updates](/docs/cloud/agent-updates#refresh-a-cluster).

## When databases restart

A release comes with new images for your [databases](/docs/databases). A database restarts once to move to its new image.

- **Postgres and KV** databases restart once after every update.
- **MySQL** databases restart only when the release has a new MySQL image.

When an update restarts databases, Pyo says **Restarts your databases once**. The line shows in the update notice, in the **Update now** dialog, and under **Refresh this cluster** on a cluster that waits.

Databases restart when their cluster's install matches the new Pyo:

- On a cluster that refreshes on its own, that's within about a minute of the update.
- On the cluster Pyo runs on, that's within a few minutes, when its server runs the command by itself.
- On a cluster that waits for the command under **Refresh this cluster**, that's when you run it. So you choose the moment.

How long a database is away depends on its replicas:

- A Postgres or MySQL database with [replicas](/docs/databases#read-replicas) restarts a replica first, then switches over to it. The primary stops only for the switch.
- A database with one instance restarts. It's away for a short time.

Each restart is recorded in the team's **Activity**, like "Restarting the database main for an update".

## Update from the server

You can also update by running the install command again on the server Pyo runs on:

```bash
curl -fsSL https://pyo.dev/install.sh | bash
```

It updates to the latest release. To choose one, add `--version`, like `bash -s -- --version 0.1.0`, or set `PYO_VERSION`.

- If the release can't update straight from your version, it tells you which version to install first.
- If the release has notices, it shows them and asks before it updates. Add `--yes`, or set `PYO_YES=1`, once you've read them. In a script, or anywhere without a terminal, the update won't start without it.
- It won't go back to an older version.
- If that release is already installed, it changes nothing.
- It keeps your data and secrets as they are.
- It checks the release's signature first, with [cosign](https://docs.sigstore.dev/cosign/system_config/installation/). If cosign isn't installed, it downloads a pinned version and checks that against its checksum.

It also updates the agent on this machine's cluster, if it's connected. Agents on other clusters stay as they are until you choose **Update now** under **Settings → Updates**. See [Agents on other clusters](#agents-on-other-clusters).

## Automatic updates

Set **Updates** to **Automatic** to install new releases in a maintenance window. Choose the **Days** and the time under **At**, both in UTC. By default, that's Sunday at 03:00.

Automatic updates never:

- install a release that needs manual steps,
- install a release that can't update straight from the version you run,
- retry a version that failed before,
- run outside the window.

You can still install those yourself with **Update now**.

## Requirements

Pyo updates itself through the agent on the cluster it runs on. Connect the machine Pyo runs on as a cluster, and keep its agent online.

If a release can't update straight from your version, the dialog tells you which version to update to first.
