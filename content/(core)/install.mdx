## Requirements

- **System:** Linux on <Term tip="The 64-bit processor type of most servers and PCs, also called amd64.">x86-64</Term>, with root or `sudo` access.
- **Resources:** at least 2 CPU cores, 2 GB of memory and 40 GB of disk. See [Memory](#memory) for how much to choose.
- **Ports:** 8000 and 5005 free, plus 80, 443 and 6443 if k3s isn't installed yet. The installer stops if one of these is taken. Only 80 and 443 need to be reachable from the internet, for your services and Pyo's dashboard.

<Term tip="A free service that issues the certificates browsers need for HTTPS. Pyo requests and renews them for you.">Let's Encrypt</Term> certificates need a machine that's reachable from the internet on ports 80 and 443. On a home network or a laptop, without [Tailscale](/docs/tailscale), Pyo and your services open over plain HTTP on your own network. See [On a home server](#on-a-home-server).

### Memory

| Memory | Good for |
| --- | --- |
| 2 GB | The minimum. Enough to try Pyo or run a few small services. Builds are slower and there's little room for databases. |
| 4 GB | Recommended for real use with databases. |
| 8 GB or more | Many services, builds on the same server and several databases. |

A [build server](/docs/builders#where-a-builder-can-run) or more [servers](/docs/servers) in the cluster spread the load. On machines with less than 3.5 GiB, the installer tunes k3s for low memory. See [k3s](/docs/system-reference#k3s).

On a 2 GB server, about 570 MiB is left for your services and databases: 512 MiB is set aside for k3s and the system, and Pyo's own parts, with k3s's DNS and metrics, ask for about 890 MiB. A small database takes 128 MiB of that, and a static site served by Caddy around 15 MiB. When a deploy doesn't fit, it fails with what it needs, what's free and the biggest requests on the server.

On machines under 3.5 GB, observability starts off. You can [turn it on](/docs/observability#turning-it-on-or-off) when you have the memory to spare.

Pyo sizes k3s and its own database by the machine's memory each time they start. After you give a machine more or less memory, restart it and they follow. See [Memory tiers](/docs/system-reference#memory-tiers).

## Install

Run this on your machine:

```bash
curl -fsSL https://pyo.dev/install.sh | bash
```

It asks for `sudo` if it needs root. It installs k3s if it isn't there yet, then the latest release of Pyo. The first install takes a few minutes.

It installs the k3s version this release of Pyo was tested with, and checks k3s's checksums before running anything. See [k3s](/docs/system-reference#k3s) for the version and how to use another.

When it finishes, the installer prints where Pyo is. See [Where Pyo is](#where-pyo-is).

It also prints a one-time login: the email `admin@pyo.local` and a password. Open the dashboard, sign in, and choose your own email and password. The printed login stops working once you do. Until then, running the install command again prints it again.

Pyo connects its own server as your first cluster, named after its hostname, and sets up a builder on it. Both are ready to use, so the dashboard takes you straight to deploying your first service.

If you lose the printed password before signing in, read it back on the server:

```bash
sudo k3s kubectl -n pyo-system get secret pyo-admin -o jsonpath='{.data.password}' | base64 -d
```

Lost your own password later? Run `sudo pyo-reset-login` on the server for a one-time link. See [Getting back in](/docs/getting-back-in).

## Where Pyo is

One server with a public IP needs no Tailscale. Pyo is at:

| Address | From |
| --- | --- |
| `https://pyo.<public-ip>.nip.io` | Anywhere, with a Let's Encrypt certificate. It takes a minute or two after the install, and the installer waits for it. A server behind NAT, with no public IP of its own, doesn't get it. |
| `http://<private-ip>:8000` | Your own network, like a home or office LAN. |
| `http://localhost:8000` | The machine itself. |

Pyo answers port 8000 only from the machine itself, private networks and your tailnet. Anything else is turned away, whatever it sends. Over plain HTTP, sign in with your password or a one-time code. [Passkeys](/docs/passkeys) need HTTPS.

Once you add a second server or another cluster, set up [Tailscale](/docs/tailscale). Pyo is then also at `https://pyo.<tailnet>.ts.net`, and you can close the public dashboard.

### On a home server

A server behind NAT, like one at home, has no HTTPS address of its own. Pyo is at its address on your network over HTTP, and so are your services. A service with no domain opens at the server's address and a port Pyo picks, like `http://192.168.1.20:31234`. Set up [Tailscale](/docs/tailscale) to get HTTPS for Pyo and your services.

## Install a particular release

The installer uses the latest release. To choose one, add `--version`, or set `PYO_VERSION`:

```bash
curl -fsSL https://pyo.dev/install.sh | bash -s -- --version 0.1.0
```

To update later, run the install command again. See [Updating Pyo](/docs/updating-pyo). To remove Pyo, see [Uninstalling Pyo](/docs/uninstall).

## Verify a script

pyo.dev serves each install script exactly as a Pyo release published it. `pyo.dev/install.sh` is the latest release's, and `pyo.dev/v/0.4.3/install.sh` is release 0.4.3's. The same goes for `connect.sh`, `join.sh`, `sandbox.sh` and `cli.sh`.

To check a script before you run it, compare its SHA-256 with the one in the release notes on [GitHub](https://github.com/upsetdev/pyo/releases):

```bash
curl -fsSLO https://pyo.dev/v/0.4.3/install.sh
sha256sum install.sh
```

The release's `release.json` lists the same sums, signed by Pyo's release workflow. To check that signature too, with [cosign](https://docs.sigstore.dev/cosign/system_config/installation/):

```bash
V=0.4.3
curl -fsSLO https://github.com/upsetdev/pyo/releases/download/v$V/release.json
curl -fsSLO https://github.com/upsetdev/pyo/releases/download/v$V/release.json.sigstore.json
cosign verify-blob release.json --bundle release.json.sigstore.json \
  --certificate-identity https://github.com/upsetdev/pyo/.github/workflows/release.yml@refs/tags/v$V \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com
grep '"install.sh"' release.json
```

Every release's signature is recorded in Sigstore's public transparency log, [Rekor](https://search.sigstore.dev), so anyone can see what was signed and when.

## Install count

When a fresh install is ready, the installer tells `api.pyo.dev` once, so we know how many people get Pyo running. It sends Pyo's version, the OS and the arch. It never sends the server's name, domains, addresses or who you are, and the source IP isn't stored. Running the command again to update sends nothing. The installer doesn't print anything about it.

To skip it, set `PYO_TELEMETRY=off`. This also starts Pyo with [usage counts](/docs/updating-pyo#usage-counts) off:

```bash
curl -fsSL https://pyo.dev/install.sh | PYO_TELEMETRY=off bash
```

You can turn usage counts on later under **Settings → Updates**.

## Securing Pyo

On a server with a public IP, Pyo's dashboard is on the internet at `https://pyo.<public-ip>.nip.io` until you close it. Follow [Securing Pyo](/docs/securing-pyo) before you put anything real on it.
