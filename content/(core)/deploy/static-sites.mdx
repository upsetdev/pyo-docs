A static site is a folder of HTML, CSS, JavaScript and images. Pyo deploys it like any other service from Git. With no Dockerfile, Pyo builds it with [Railpack](https://railpack.com). The build log says **Static site** for plain files, or the framework's name for a built frontend.

## Served as static files

When the build is a static site, Pyo serves its files from Pyo Static, a small file server it runs on the cluster, instead of a service of its own:

- **Instant deploys and rollbacks:** each deploy is its own folder of files. A deploy or a rollback only moves the site's domains to another folder, so nothing restarts.
- **No replicas to run:** one server, `pyo-static`, serves every static site of the cluster. It runs only while the cluster has one.
- **Up when storage isn't:** the files are kept in your team's storage on the server Pyo runs on, and `pyo-static` keeps a copy on its own server's disk. A site keeps answering while that storage can't be reached.
- **Everything else works the same:** [domains](/docs/domains) and HTTPS, free domains, the [firewall](/docs/firewall), the [WAF](/docs/waf), [analytics](/docs/observability) and [deploy on every push](/docs/deploy#deploy-on-every-push).

The build log says **Uploading the site** with its files and size, and the service shows **Static files** instead of its replicas. Its **Logs** show each request, with its path, status and time.

Only Railpack's static builds are served this way. A Dockerfile build always runs as a service, and so does a build that isn't a static site.

### Run it as a service instead

To serve the site with its own Caddy service, as Pyo did before, turn off **Serve as static files** in the service's **Settings**, under **Static files**, then redeploy. Turn it on again the same way. The switch works both ways without downtime: the domains move to the new version only once it's ready.

With the CLI, set `"serveAs": "service"` or `"serveAs": "static"` under `deploy` in [pyo.jsonc](/docs/cli/pyo-jsonc).

### Limits

A static site can have up to 20,000 files and 1 GiB in all, and each file up to 90 MiB. That keeps each file under Cloudflare's 100 MB limit for one request. A bigger one runs as a service, and the build log says why. Pyo keeps the files of each site's 10 newest deploys for rollbacks. Rolling back to an older deploy runs it as a service from its image.

## Headers and redirects

Put a `_headers` or `_redirects` file at the root of the output folder, as on Netlify and Cloudflare Pages. Pyo supports the part of their syntax described here. The build log names each line it leaves out, and neither file is served to visitors.

### `_redirects`

One rule per line: a path, where it goes, and a status. Lines starting with `#` are comments.

```text title="_redirects"
/old            /new
/blog/*         /posts/:splat     302
/users/:id      /profile/:id
/docs           https://docs.example.com
/app/*          /app/index.html   200
/gone/*         /404.html         404
```

- **Status:** `301` when there's none. `302`, `303`, `307` and `308` redirect too. `200` serves the target's file at the same address, and `404` serves it with a `404`.
- **Patterns:** `*` at the end matches the rest of the path, and `:splat` puts it in the target. `:name` matches one part of the path, and `:name` in the target puts it there.
- **Order:** the first rule that matches wins. A redirect applies even where a file is. A `200` rule applies only where no file is.
- **Query strings:** a redirect keeps the request's query string, unless the target has one.
- **Not supported:** conditions like countries, languages or cookies, matching on query strings, and `200` to another site. A `!` after the status is accepted and changes nothing.

### `_headers`

A path on its own line, then the headers its responses get, each on its own indented line:

```text title="_headers"
/*
  X-Frame-Options: DENY
  Referrer-Policy: strict-origin-when-cross-origin

/assets/*
  Cache-Control: public, max-age=31536000, immutable
  ! X-Frame-Options
```

- **Patterns:** the same as in `_redirects`, and `:splat` or `:name` in a value puts that part of the path there.
- **Several matches:** every block that matches applies, in order. A header two blocks set gets both values, joined with a comma. `! Name` takes away a header an earlier block set.
- **Not allowed:** headers the server sets itself, like `Content-Length` and `Content-Encoding`.

Without a `_headers` file, each file gets its `Content-Type` from its extension, an `ETag`, and `Cache-Control: public, max-age=0, must-revalidate`, so browsers check for a new version on each visit.

## Before you deploy

Keep the default port, `8080`. Pyo sets `PORT` to the service's first port, and Railpack's Caddy listens on `PORT` when the site runs as a service.

## Health check

When the build finds a static site that runs as a service, Pyo checks that `/` answers before the new version takes traffic. A redirect counts too. The service's **Health check** shows **Automatic (static site)**. A site served as static files needs no check: it goes live once `pyo-static` has its files.

To use another check, change it on the service's **Resources** tab. Pyo then keeps yours. Choose **HTTP path** for another path, **TCP** to only wait for the port, or **None** to not wait at all.

## Plain HTML

Push a repository with an `index.html` at its root, and that's it. Pyo serves the whole repository, except `.git` and `.env` files.

To serve another folder, Railpack looks in this order:

1. A `RAILPACK_STATIC_FILE_ROOT` build argument, like `site`.
2. A file named `Staticfile` at the root, with `root: site`.
3. A `public` folder.
4. An `index.html` at the root.

A request for `/about` finds `about`, `about.html` or `about/index.html`.

## A built frontend

Pyo runs your `build` script, then serves only its output. Railpack finds the output folder for:

- **Vite**, including React, Vue and Svelte projects built with Vite
- **Astro**, when it has no server output or adapter
- **Next.js** with `output: 'export'`
- **Create React App**
- **Angular**

It reads a custom `outDir` from your Vite or Astro config. For anything else, like SvelteKit with `adapter-static`, add a build argument with the output folder:

```bash
RAILPACK_SPA_OUTPUT_DIR=build
```

That also tells Railpack to serve the folder as a static site, whatever the framework. Variables your build reads, like `VITE_API_URL`, go in build arguments too, since the build runs before the service starts.

Add build arguments in **Deploy new**, under **Advanced: Dockerfile, build context and arguments**, or later in the service's **Settings**, under **Deployment source**. They're used on the next deploy. To change the build command, add `RAILPACK_BUILD_CMD`, like `npm run build:prod`.

## Static site generators

Many generators' `start` script runs their development or preview server, like `eleventy --serve`, `astro dev`, `vite preview` or `hugo server`. That's a full Node.js process, often 100 MiB of memory or more, to serve files. When Pyo finds one, it runs your `build` script and serves the output with Caddy instead, in around 15 MiB:

| Generator | Output folder |
| --- | --- |
| **Eleventy** | `_site`, or the `output` in your Eleventy config or `--output` in the build script |
| **Astro**, with no server output or adapter | `dist`, or `outDir` in your Astro config |
| **Hugo**, built through npm (like `hugo-bin`) | `public`, or `-d` in the build script |
| **Vite** | `dist`, or `outDir` in your Vite config |

Eleventy and Hugo are served this way with no `start` script too. The build log says which folder it serves.

A generated site has a page for each path, so a path that matches nothing gets a `404` instead of the home page. A `Staticfile` of your own changes that.

To run your `start` script instead, add the build argument:

```bash
RAILPACK_NO_SPA=1
```

Pyo also leaves it alone when you set `RAILPACK_SPA_OUTPUT_DIR`, `RAILPACK_START_CMD` or `RAILPACK_STATIC_FILE_ROOT`, or have a `Procfile` or a start command in `railpack.json`.

Jekyll, and Hugo without a `package.json`, need a [Dockerfile](#your-own-dockerfile), since Railpack can't build them on its own.

## Routing in single page apps

A single page app handles its own paths, like `/settings`, so every path that isn't a file should get `index.html`.

- **A built frontend:** this is on by default, except for a [static site generator](#static-site-generators)'s output that Pyo serves.
- **Plain HTML:** turn it on with a `Staticfile` at the root:

```yaml
root: .
index_fallback: true
```

Set `index_fallback: false` to turn it off for a built frontend. Without the fallback, a path that matches nothing gets a `404`, or your `404.html` for plain HTML sites.

## A site in a subfolder

If the site lives in a folder of a bigger repository, set the **Build context** to that folder, like `apps/web`. Pyo builds and serves it from there.

## Your own Dockerfile

If you add a Dockerfile, Pyo uses it instead of Railpack. This one builds a Vite site and serves it with nginx on port `8080`, with every unknown path going to `index.html`:

```dockerfile title="Dockerfile"
FROM node:22-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM nginx:1.27-alpine
COPY nginx.conf /etc/nginx/conf.d/default.conf
COPY --from=build /app/dist /usr/share/nginx/html
```

```nginx title="nginx.conf"
server {
    listen 8080;
    root /usr/share/nginx/html;

    location / {
        try_files $uri $uri/ /index.html;
    }
}
```

Set the health check to **HTTP path** `/`, since Pyo only picks one for Railpack's static sites. Pyo passes your build arguments to the Dockerfile as `ARG` values.

## The Nginx template

[Templates](/docs/templates) has **Nginx**. It serves nginx's welcome page on port `80`, and is a starting point for your own image: build one `FROM nginx` with your files in `/usr/share/nginx/html`, then deploy it from Git or a [container image](/docs/deploy#from-a-container-image).

## Good to know

- **Served from your servers:** the files come from your servers, not a global <Term tip="A content delivery network keeps copies of your files in many places around the world, so they load fast everywhere.">CDN</Term>. For visitors far from them, put a CDN like Cloudflare in front.
- **Inside the cluster:** a site served as static files has no address of its own inside the cluster. Other services reach it at its domain.
- **As a service:** a site that [runs as a service](#run-it-as-a-service-instead) is a small service that's always on, with its own replicas and resources. See [Scaling](/docs/scaling).
- **Security headers:** for plain HTML sites that run as a service, Railpack's Caddy adds a few headers, including a `Content-Security-Policy`. If it blocks something your site needs, use your own Dockerfile. Served as static files, a site gets only the headers its [`_headers`](#_headers) sets.
