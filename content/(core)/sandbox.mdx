A sandbox is an isolated machine you create through an API. Create one, run commands, read and write files, open a port as a URL, then throw it away. Use them for:

- AI agents that write and run code.
- Code interpreters.
- Previews of a branch or a change.
- CI jobs and other code you don't trust.

Sandboxes run on your own infrastructure, so your code and data never leave it. They show in the same dashboard as your services and databases.

## How sandboxes run

Sandboxes run on their own **sandbox servers**, outside your clusters and build servers. A sandbox server runs no k3s or Docker, just a small Pyo daemon, so a busy sandbox can't slow down your services.

On a server with KVM, each sandbox is its own <Term tip="A very small virtual machine that boots in milliseconds, with its own kernel.">microVM</Term> on [Firecracker](https://firecracker-microvm.github.io), with its own kernel. On a server without KVM, like a cloud VPS, each sandbox runs under [gVisor](https://gvisor.dev), which gives it a kernel of its own in user space. Sandboxes never run as plain containers.

Your code asks Pyo to create a sandbox, then talks to the sandbox server directly to run commands and move files, with a short-lived token Pyo signs. Pyo isn't in the way of each command, and sandboxes keep working while Pyo itself restarts.

The sandbox server answers on your [tailnet](/docs/tailscale). So the code that runs commands in a sandbox, and the browser you open its terminal in, need to be on your tailnet too. Only the ports you open are on the web.

### KVM or gVisor

Each time a sandbox server starts, Pyo checks what it can run:

- **Firecracker on KVM.** The server has KVM and a test microVM boots in under 300 ms. This is the fastest.
- **Firecracker on nested KVM.** The server is itself a VM with KVM passed through. The test boot is slower, so sandboxes start slower too.
- **gVisor.** The server has no usable KVM, like most cloud VPSs, but can run [gVisor](https://gvisor.dev).

A server with neither is turned away when it joins, with the reason. If a server loses KVM, it becomes a gVisor server at its next start. The **Clusters** page shows each sandbox server's runtime with a one-line summary. So do `pyo sandbox servers ls` and `runtime` in the API.

A sandbox's **Isolation** is **Auto** by default, which picks Firecracker first. **VM only** (`isolation: "vm"`) never runs it on gVisor.

### What gVisor can't do

Sandboxes on gVisor run the same templates and have the same commands, files, terminals, ports, network rules, limits, lifetimes and pause. These differ from Firecracker:

- **Cold starts.** A sandbox starts from its template's disk in about 40 ms. Firecracker restores a running snapshot, so a template can't have a process already warm in it on gVisor.
- **Slower system calls.** Each command and each process start costs more. A command takes about 5 ms instead of under 1 ms, and starting Python takes 4 to 5 times as long. For a code interpreter, keep one interpreter running and send it code.
- **Not every Linux feature.** gVisor runs most programs, but some system calls and parts of `/proc` and `/sys` are missing. Docker doesn't fully work inside a sandbox, and nothing can run a VM inside one.
- **Pause needs the same gVisor release.** A paused sandbox resumes only under the gVisor release it was paused under. An update that changes it ends the pauses on that server.
- **No VM only.** A sandbox created with `isolation: "vm"` never runs on a gVisor server.
- **More disk for the server.** gVisor's files take about 180 MB on the server.

## Add a sandbox server

Open **Sandboxes** in the dashboard and choose **Add a sandbox server**. Team owners and admins can add one. There are two ways:

- **Cloud provider.** Pyo buys a server for you and sets it up.
- **Command line.** You run one command on a server you have.

Either way you need [Tailscale](/docs/tailscale) set up in Pyo, since sandbox servers join over your tailnet.

### Cloud provider

Pyo makes the server in your team's [Hetzner](/docs/hetzner) project, the same way it makes a cluster's servers there:

1. Pick the provider. If your team hasn't connected Hetzner yet, paste a project API token with **Read & Write** right there. See [Make a token](/docs/hetzner#make-a-token).
2. Name the server, and give it an [edge domain](#edge-domain) if you want sandbox ports on the web.
3. Pick a location and a server type. Pyo reads the types, their vCPUs, memory, disk and monthly prices from Hetzner as you pick. Prices are before VAT and include the IPv4 address.
4. Choose **Create**. Pyo shows the monthly price and asks once more.

The page then follows the server: **Creating**, **Booting**, **Joining**, **Ready**. On its first boot the server joins your tailnet with a single-use key, gets a one-time join code from Pyo over the tailnet and runs `sandbox.sh` with it. Nothing else secret is in its setup. If your tailnet has Tailnet Lock on, Pyo shows the command to sign the server. You can leave the page while it sets up. The **Sandboxes** page shows its progress too.

Hetzner Cloud servers have no KVM, so they run sandboxes on [gVisor](#what-gvisor-cant-do). Pyo puts them behind a Hetzner firewall that lets in only the web (80 and 443) and Tailscale, and they run nothing else.

From the CLI:

```bash
pyo server types --location fsn1
pyo sandbox servers create sbx-1 --location fsn1 --type cx22
```

Removing the server in Pyo ends its sandboxes, takes it off your tailnet and deletes it at Hetzner. Pyo shows the monthly cost that stops and asks first.

### Command line

A server of your own needs:

- Linux on x86-64 or arm64, with kernel 5.10 or newer and cgroup v2
- KVM for Firecracker, or else root for gVisor
- a machine of its own. A machine with k3s on it is turned away.

Choose **Command line**, or use the CLI:

```bash
pyo sandbox servers add sbx-1
```

Pyo gives you a command to run on the new machine as root. It looks like this:

```bash
curl -fsSL https://your-pyo/install/sandbox.sh | bash -s -- \
  --pyo pyo.tail1234.ts.net:5006 --server sbs_abc123 --name sbx-1 \
  --code 9f2c... --tailscale-key tskey-auth-... --version 0.4.0
```

It joins your tailnet, installs the daemon, Firecracker and the guest kernel, checks what the server can run and joins Pyo. A server without KVM gets gVisor too, and is checked again. The join code works once, for 15 minutes. When it expires, the dashboard says **This command expired**. Choose **Get a new command** for a fresh one, and the old one stops working.

The server's daemon answers only on your tailnet. Only ports 80 and 443 are public, for the edge proxy that serves sandbox ports.

Sandbox servers show on the **Clusters** page as their own group, with their runtime, CPUs, memory, disk and sandboxes.

### How the files are checked

The sandbox server's files come with each Pyo release. Before anything changes on the server, `sandbox.sh` checks the release's `release.json` against its Sigstore signature, as the [installer](/docs/updating-pyo#check-for-updates) does. Then it checks the files against the SHA-256 that `release.json` lists for that architecture in its `sandbox` field, and gVisor's files against its `sandboxGvisor` field. gVisor is a pinned release, checked against its own SHA-512 when Pyo's release is made. If anything doesn't match, nothing is installed.

### sandbox.sh options

The dashboard fills in the options that join the server. These change how it installs:

| Option | What it does |
| --- | --- |
| `--version X` | The Pyo release whose sandbox files to install, like `0.4.0`. |
| `--bundle FILE` | Sandbox files from a file or URL instead of the release. Also `PYO_SANDBOX_BUNDLE`. They're checked against `--bundle-sha256`, or else against the signed `release.json` of `--version`. |
| `--bundle-sha256 SUM` | The SHA-256 to check `--bundle` against. Also `PYO_SANDBOX_BUNDLE_SHA256`. |
| `--gvisor-bundle X` | gVisor's files from a file or URL instead of the release, for a server without KVM. Also `PYO_SANDBOX_GVISOR_BUNDLE`. They're checked against the signed `release.json` of `--version`. |
| `--dev` | Skip the check, for files you built yourself. Also `PYO_SANDBOX_DEV=1`. |
| `--edge-domain D` | Serve sandbox ports at `<port>-<sandbox>.D` on ports 80 and 443. Also `PYO_SANDBOX_EDGE_DOMAIN`. See [Edge domain](#edge-domain). |
| `--edge-cert FILE` | The certificate for `*.D`, as PEM with the full chain. Default `/etc/pyo-sandbox/edge/cert.pem`. |
| `--edge-key FILE` | Its private key. Default `/etc/pyo-sandbox/edge/key.pem`. |

To update the daemon, run the command again with a newer `--version`. A server that has joined needs no code then, and running sandboxes keep running. A gVisor server gets the release's gVisor too.

To take Pyo off the server, remove it on the **Clusters** page or with `pyo sandbox servers rm`, then run this on it:

```bash
curl -fsSL https://your-pyo/install/sandbox.sh | bash -s -- --uninstall
```

Its sandboxes end. Tailscale stays.

## Edge domain

Opened ports are served by the sandbox server's edge proxy, at `https://<port>-<sandbox>.<edge domain>`, like `https://3000-sbx-abc.sbx.example.com`. Give a server an edge domain when you add it, under **Edge domain**, or with `--edge-domain`. Without one, ports can't be opened on that server.

The edge domain needs a wildcard DNS record, `*.sbx.example.com`, pointing at the server's public address. HTTPS needs a wildcard certificate for it.

### With Cloudflare

When your [Cloudflare](/docs/cloudflare) connection can edit the domain's zone, the server's menu on the **Clusters** page offers:

- **Create DNS record**, which adds the wildcard record pointing at the server's public addresses, not proxied. A record already on that name is never changed.
- **Get certificate**, which gets a wildcard certificate from Let's Encrypt and puts it on the server. Pyo renews it 30 days before it runs out. **Renew certificate** renews it now.

Pyo gets the certificate itself, so your Cloudflare token never goes to the sandbox server.

### Your own certificate

Without Cloudflare, put a wildcard certificate on the server yourself, at `/etc/pyo-sandbox/edge/cert.pem` and `/etc/pyo-sandbox/edge/key.pem`, or the paths you gave with `--edge-cert` and `--edge-key`. The edge serves it within a minute, with no restart. Until there's a certificate, ports are served over plain HTTP.

## Templates

A sandbox starts from a sandbox template, made from a container image. Find them under **Sandbox templates**, in the sidebar's **Sandboxes** menu, or use the CLI:

```bash
pyo sandbox templates create node-22 node:22
```

The image can be public on any registry, or in [Pyo's registry](/docs/registries#push-your-own-images). Every sandbox server that may use the template pulls the image and unpacks it. A Firecracker server then boots it once and saves a snapshot to start sandboxes from. A gVisor server starts each sandbox from the unpacked disk. A template is ready once one server has it. Each template shows its state on each server: pending, building (pulling, unpacking or snapshotting), ready or failed, with its size once ready.

An image may take up to 10 GiB, and the server needs the disk space to unpack it. A server builds one template at a time.

Templates belong to your team, or to the installation, which every team can use. Deleting a template removes it from the servers that made it.

## Networking

A sandbox has the internet by default. Choose **No network** (`network: "none"`) for a sandbox with no network at all. Opened ports still work then, since the edge reaches them through the sandbox server, not the network.

A sandbox with network can't reach:

- the sandbox server itself, on any of its addresses
- your tailnet
- other sandboxes
- private and link-local ranges, like `10.0.0.0/8`, `192.168.0.0/16` and `169.254.169.254`
- anything over IPv6

DNS goes to `1.1.1.1` and `8.8.8.8`. Nothing from outside can open a connection into a sandbox. Only replies come back.

Sandboxes get addresses from `198.18.0.0/16`, a range nothing routes. If that overlaps the server's own networks, the daemon won't turn networking on. To change the range or the DNS servers, or to block more ranges, edit `/etc/pyo-sandbox/local.json` on the server and restart `pyo-sandbox`.

### Docker and ufw on the server

Docker and ufw set the server's forwarding policy to drop. When it is, the daemon adds two rules of its own, to `DOCKER-USER` when Docker made it, or else to `FORWARD`, so sandbox traffic gets out and its replies come back. It never changes the policy itself. With ufw active, `sandbox.sh` also opens the daemon's port on `tailscale0`, and ports 80 and 443 for the edge. Any other firewall in front of the server needs 80 and 443 open too.

## Limits

Each sandbox can have:

| | Default | Range |
| --- | --- | --- |
| CPUs | 1 | 1 to 32 |
| Memory | 512 MiB | 128 MiB to 64 GiB |
| Disk | 2 GiB | 64 MiB to 256 GiB |
| Lifetime | 5 minutes | up to 24 hours |

A sandbox ends when its lifetime runs out. Extend it while it runs.

Each team also has limits on all its sandboxes together. Paused ones count.

| Limit | Default |
| --- | --- |
| Sandboxes at once | 10 |
| CPUs | 16 |
| Memory | 16 GiB |
| Disk | 100 GiB |
| Longest lifetime | 24 hours |

The installation's admin changes them in the team's **Settings**, under **Sandboxes**. Setting **Sandboxes at once** to 0 turns sandboxes off for the team.

## Use sandboxes

An [API key](/docs/api#what-a-key-can-do) needs **Sandboxes** or **Full** access to use sandboxes. **Sandboxes** access can read, and create and use sandboxes, but change nothing else.

### TypeScript SDK

Install `@pyodev/sandbox`:

```bash
npm install @pyodev/sandbox
```

It reads `PYO_URL`, `PYO_API_KEY` and `PYO_TEAM` from the environment, or takes them as options. It works in Node 20 and later, and in Bun.

```ts
import { Sandbox } from "@pyodev/sandbox";

const sbx = await Sandbox.create({ template: "node-22", ttl: "1h" });

// Commands
const r = await sbx.exec("node -v");
console.log(r.stdout, r.exitCode);

// Files
await sbx.files.write("/app/index.js", "console.log('hi')");
const text = await sbx.files.read("/app/index.js");

// A terminal
const pty = await sbx.pty({ cols: 120, rows: 30, onData: (b) => process.stdout.write(b) });
pty.write("ls\r");

// Ports
await sbx.spawn("npx serve -l 3000");
const url = await sbx.ports.open(3000);

await sbx.delete();
```

- **Commands:** `exec` waits for a command and returns its output and exit code. A command times out after 60 seconds unless you set `timeoutMs`, and keeps up to 8 MiB of each output. `spawn` starts one and returns at once, for servers and interactive input.
- **Files:** read, write, list, stat and remove files. Each call moves up to 64 MiB.
- **Terminals:** `pty` opens a terminal, with resize.
- **Ports:** `ports.open` returns the port's URL on the [edge](#edge-domain). A private port, with `{ public: false }`, needs the sandbox token on each request. `ports.connect` opens a TCP connection to a port inside the sandbox, even with no network.
- **Lifetime:** `extend`, `pause`, `resume` and `delete`. A paused sandbox keeps its memory and files and resumes where it was.

The token for the sandbox server lasts an hour. The SDK gets a new one from Pyo five minutes before it runs out. To use a sandbox from a browser without an API key, your backend passes on `sbx.connection()` and refreshes the token for it.

The SDK also has ready-made tools for the Claude API and the Vercel AI SDK. See its [README](https://github.com/upsetdev/pyo-sandbox-js) for every option.

### MCP

Once your team can use a sandbox server, [MCP](/docs/mcp) gets sandbox tools, so an assistant can run code for you in a sandbox. Give the assistant **Sandboxes** or **Full** access.

| Tool | What it does |
| --- | --- |
| `create_sandbox` | Creates a sandbox and returns its id |
| `run_code` | Runs Python, Node or Bash code and returns its output |
| `exec` | Runs a shell command |
| `read_file` and `write_file` | Read and write a file |
| `open_port` and `close_port` | Serve a port at a URL, or stop serving it |
| `pause_sandbox` | Pauses a sandbox |
| `delete_sandbox` | Ends a sandbox and throws away its files |

These go through Pyo, so the assistant doesn't need your tailnet. See the [full tool list](/docs/mcp/tools).

### CLI

The [`pyo` CLI](/docs/cli) has `pyo sandbox`:

```bash
pyo sandbox create node-22 --ttl 30m
pyo sandbox exec sbx_abc123 "node -v"
pyo sandbox shell sbx_abc123
pyo sandbox cp ./app.js sbx_abc123:/app/app.js
pyo sandbox ports open sbx_abc123 3000
pyo sandbox rm sbx_abc123
```

It also has `ls`, `get`, `pause`, `resume`, `extend` and `token`, and `servers` and `templates` to manage those. `exec`, `shell` and `cp` reach the sandbox server directly, so they need your tailnet. See the [command reference](/docs/cli/commands#pyo-sandbox).

### Dashboard

The **Sandboxes** page lists your sandboxes. **New sandbox** creates one, and shows the same choices as SDK code, ready to copy. A sandbox's page has its **Overview** with its ports, a **Terminal**, its **Files**, the **Commands** it ran and its **Metrics**.
