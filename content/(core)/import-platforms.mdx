---
title: Importing from another platform
description: Move your services, Compose stacks and databases from Coolify, Dokploy, Railway or Vercel into Pyo.
---

Pyo can bring your services over from Coolify, Dokploy, Railway or Vercel. It reads them through the platform's API, shows you what each one becomes, and imports the ones you pick. Owners and admins can import.

## Before you start

Make a token on the platform:

- **Coolify:** in **Keys & Tokens**, make an API token with `read` and `read:sensitive`. Without `read:sensitive`, Coolify doesn't share variable values. If the API is off, turn it on in **Settings**.
- **Dokploy:** in your profile's **API/CLI** section, generate an API key.
- **Railway:** in **Account Settings**, then **Tokens**, make a token. A workspace or project token works too. A project token reads one environment of one project.
- **Vercel:** in **Account Settings**, then **Tokens**, make a token.

Pyo uses the token only while it reads, and never stores it.

## Import

### From the dashboard

1. Choose **New → Import from a platform**.
2. Pick the **Platform** and enter its **API token**. Coolify and Dokploy also need their **Address**. For Vercel, enter a **Team** (its slug or id) to read that team instead of the token's own scope. Pick the **Cluster** to run on, then choose **Preview**.
3. Check what each project, service and database becomes. Notes say what doesn't carry over.
4. Pick what to bring. Turn on **Deploy services once imported** to deploy them now. Otherwise they're saved stopped, ready to deploy.
5. Choose **Import**. Each item shows **Created**, **Copying data**, **Imported before**, **Held**, **Not imported** or **Failed**. One failure doesn't stop the others.

### From the CLI

```bash
pyo import coolify --from https://coolify.example.com --source-token <token>
```

```bash
pyo import railway --source-token <token>
pyo import vercel --source-token <token> --source-team <team>
```

The CLI shows what it will create and asks before it imports. Use `dokploy` for Dokploy. Railway and Vercel need no `--from`, and `--source-team` is optional. Add `--team` or `--cluster` to choose where it goes, `--deploy` to deploy the services, and `--yes` to skip the question.

### From the API

Send the platform's token, and its address for Coolify or Dokploy, to [Preview an import from another platform](/docs/api/reference/projects/preview-platform-import) to see the plan. Then import the items you pick with [Import from another platform](/docs/api/reference/projects/start-platform-import).

## What comes over

- **Projects:** each project becomes a Pyo project. An environment other than production becomes a project of its own, named after both.
- **Applications:** each becomes a service, built from its repository (with its Dockerfile, or with zero config) or run from its image. A GitHub repository builds through your team's [GitHub App](/docs/github) when it can reach it.
- **Variables:** with secret ones encrypted. Values that are locked in Coolify can't be read: they come over empty, so set them in Pyo.
- **Domains:** they go live once the service is deployed. Point their DNS at Pyo when you're ready to switch. Domains the platform made up for you, like `sslip.io` ones, are left out.
- **Ports:** published ports become public TCP or UDP ports through the [gateway](/docs/gateway), when Pyo allows that port.
- **Volumes:** they start empty. Copy their data yourself.
- **Compose stacks:** each becomes a project of its own, as with a [Docker Compose import](/docs/deploy/compose). A Compose file from a repository isn't imported: use the Compose import from the repository.
- **Databases:** Postgres and MySQL databases the platform makes reachable from outside are copied into new Pyo [databases](/docs/databases), as in [Migrating a database](/docs/migrating). Others are made empty, with how to move their data. Redis, KeyDB and Dragonfly become empty KV databases. MariaDB, MongoDB, ClickHouse and libSQL aren't imported.

### From Railway

- **Projects:** each environment other than production becomes a project of its own, as above. Pull request environments are left out.
- **Services:** each is built from its repository or run from its image. One Railway built with buildpacks is built with zero config.
- **Variables:** references like `${{shared.KEY}}` are filled in. `RAILWAY_PRIVATE_DOMAIN` becomes the service's name in Pyo and `RAILWAY_PUBLIC_DOMAIN` its first custom domain. Sealed variables come over secret and empty, so set them in Pyo.
- **Databases:** Postgres and MySQL with public access turned on are copied. Redis becomes an empty KV database. MongoDB isn't imported.
- A service Railway ran on a schedule, or put to sleep when idle, keeps running in Pyo. Make a cron job for a scheduled one.

### From Vercel

- **Projects:** each becomes a service built with zero config from its Git repository, on port 3000. Its build and install commands and Node.js version come with it. A project deployed with Vercel's CLI, with no repository, needs one.
- **Variables:** production ones come over. Sensitive variables come over by name, secret and empty, so set them in Pyo. Vercel's own variables like `VERCEL_URL` aren't set. The build gets only public variables like `NEXT_PUBLIC_` ones. Add others as build arguments if the build needs them.
- **Databases:** a Postgres store is copied when Vercel shares its URL. Otherwise it's made empty. A Redis store becomes an empty KV database. Blob stores aren't carried over.
- **Runs as a server:** Next.js runs as one server with `next start`, middleware and image optimization included. Vercel Functions and Edge Functions don't run in Pyo. Pyo serves what the build makes.
- Cron jobs, password protection and preview deployments aren't carried over. Each one is a note on its item.

## Databases your services use

When a service's variable points at a database you import, like a `DATABASE_URL` with that database's host, Pyo [connects](/docs/databases) the new database to the service in place of that variable. The preview says so for each one. With **Deploy services once imported**, the first deploy waits until the database is ready and its data is copied, so the service starts on the new database.

The service gets the database's own variables. A `DATABASE_URL` stays `DATABASE_URL` and a Postgres service also gets `DATABASE_URL_DIRECT`. Variables with other names keep their names with the new values. For example `DATABASE_PUBLIC_URL` gets the new URL, and `PGHOST`, `PGUSER` and the others get its host, user and so on.

Pyo doesn't deploy a service when it can't tell which database a variable points at, or when that database isn't part of the import. The service is created and shows **Held** with the reason, for example "DATABASE_URL points at a database Pyo couldn't match." Connect a database to it, then deploy it. Other services still deploy. A variable that points at a database outside the platform, like a hosted Postgres, is left as it is.

Start, build and install commands, build secrets, file mounts, deploy keys, preview environments, labels and custom Docker options don't carry over. Each one is a note on its item.

## Run it again

You can import again at any time. What was imported before is left alone, and new services join the project the first import made.
