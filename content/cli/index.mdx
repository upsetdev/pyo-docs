title: The pyo CLI
description: Deploy and manage your services from a terminal or CI.
---

The CLI is separate from Pyo itself. Pyo runs on your server, and the CLI runs on your computer or in <Term tip="Continuous integration: a service like GitHub Actions that runs your tests and deploys on each push.">CI</Term>.

## Install

On Linux and macOS:

```bash
curl -fsSL https://pyo.dev/cli.sh | sh
```

It downloads the CLI for your system from Pyo's latest release on GitHub and checks it against the release's checksum. It works on Linux and macOS, on both x86-64 and Arm. It installs to `/usr/local/bin` when you can write there, and `~/.local/bin` otherwise. Set `PYO_INSTALL_DIR` to choose another folder, or `PYO_VERSION` for a release other than the latest.

### Windows

In PowerShell:

```powershell
$dir = "$env:LOCALAPPDATA\Programs\pyo"
$url = "https://github.com/upsetdev/pyo/releases/latest/download/pyo-windows-x86_64.exe"
New-Item -ItemType Directory -Force $dir | Out-Null
$ProgressPreference = "SilentlyContinue"
Invoke-WebRequest $url -OutFile "$dir\pyo.exe"
Invoke-WebRequest "$url.sha256" -OutFile "$dir\pyo.exe.sha256"
$want = (Get-Content "$dir\pyo.exe.sha256").Split(" ")[0]
Remove-Item "$dir\pyo.exe.sha256"
if ((Get-FileHash "$dir\pyo.exe").Hash -ne $want) { Remove-Item "$dir\pyo.exe"; throw "The download doesn't match its checksum. Try again." }
$path = [Environment]::GetEnvironmentVariable("Path", "User")
if ($path -notlike "*$dir*") { [Environment]::SetEnvironmentVariable("Path", "$path;$dir", "User") }
```

This installs `pyo.exe` in your user folder and adds it to your `Path`. Open a new terminal to use it. The CLI runs on Windows on x86-64.

### Download it yourself

Each [release on GitHub](https://github.com/upsetdev/pyo/releases) has the CLI for every system, each with a `.sha256` checksum:

| System | File |
| --- | --- |
| Linux, x86-64 | `pyo-linux-x86_64` |
| Linux, Arm | `pyo-linux-aarch64` |
| macOS, Apple silicon | `pyo-macos-aarch64` |
| macOS, Intel | `pyo-macos-x86_64` |
| Windows, x86-64 | `pyo-windows-x86_64.exe` |

Rename it to `pyo` (or `pyo.exe` on Windows) and put it in a folder on your `PATH`. On Linux and macOS, make it runnable with `chmod +x pyo`.

<Callout type="warn">
  macOS blocks a CLI you download in a browser from opening. Clear the block with `xattr -d com.apple.quarantine pyo`. The `curl` install above doesn't need this.
</Callout>

On other systems, build the CLI from source with `cargo build --release -p pyo-cli`.

## Sign in

```bash
pyo login --url https://your-pyo
```

This shows a code and opens your browser. Type the code there to approve the sign-in. It works over SSH too: open the link it prints on any device. It makes an API key for this computer that lasts a year. Run `pyo login` again for a new one. It remembers your Pyo, so `--url` is only needed the first time. Without it, it asks for the address. Use `--expires` to choose 30d, 90d, 1y or never.

Your Pyo shows these commands with its own address under **API keys**.

## Link a folder

Choose which service this folder deploys. This writes [`pyo.jsonc`](/docs/cli/pyo-jsonc).

```bash
pyo link
```

## Deploy

```bash
pyo deploy
```

This applies `pyo.jsonc`, deploys and follows the <Term tip="The switch from the old version to the new one, which Pyo watches until the new version is running.">rollout</Term> to the end. The build and deploy logs show as it goes, and `pyo deploy` exits with an error when the deploy fails. Use `--detach` to start it and exit.

### Another service

Commands work on the service `pyo.jsonc` is linked to. Pass `-s` to name another one:

```bash
pyo deploy -s shop/worker
```

The folder's `pyo.jsonc` belongs to its own service, so its settings don't apply to the one `-s` names. `pyo deploy` says so and deploys without them. A deploy that would send this folder to the other service stops instead, so its files never go there. Run that deploy from the other service's own folder.

## Deploy a folder

You don't need a Git repository. In a folder no service is linked to, `pyo deploy` makes a service from it:

```bash
cd my-app
pyo deploy
```

It asks for a name (the folder's by default) and a project, creates the service, links the folder in `pyo.jsonc` and deploys it. In CI, pass `--name` and `--project` instead (a project that doesn't exist yet is created). `--team` and `--cluster` choose where it runs.

The folder is packed and uploaded to Pyo, which hands it to a builder in the service's cluster. It's built like a repository: with its Dockerfile, or without one by detecting the language. Pyo deletes the upload once the builder has it.

```text
✓ Packed 214 files, 1.8 MB
✓ Uploaded 1.8 MB
✓ Created acme/shop/my-app and linked it in pyo.jsonc
Deploying my-app https://your-pyo/acme/deployments/dpl_8f2k1m3x9q
```

Run `pyo deploy` again to send the folder as it is now. The dashboard shows each of these deployments as **Uploaded from** your computer's name, and you can roll back to any of them.

What's sent:

- Every file in the folder, except what `.gitignore` leaves out. A `.pyoignore` file, written like a `.gitignore`, leaves out more, or keeps something back in with `!`.
- Never `.git`. Never `node_modules`, unless `.pyoignore` keeps it with `!node_modules/`.
- No `.env` files, since they usually hold secrets. `.env.example` and the like are sent. Pass `--include-env` to send `.env` files too, or set the variables with `pyo env push` instead.
- At most 500 MB, packed. A bigger folder stops before it uploads and says what's biggest.

A service built from Git deploys its branch as usual. To try your working copy on it without a commit, send the folder instead:

```bash
pyo deploy --local
```

## Everyday commands

```bash
pyo status            # state, live version and domains
pyo logs --follow     # follow the logs
pyo env set KEY=value # set a variable
pyo rollback          # put back the previous version
pyo exec              # open a shell in the service
pyo open              # open it on the dashboard
```

## Logs

```bash
pyo logs                      # the last lines of every replica
pyo logs -f                   # and new ones as they come
pyo logs --since 10m          # only the last 10 minutes
pyo logs --replica x2kfp      # one replica
pyo logs --build              # the latest deployment's build and deploy log
pyo logs --build -f           # followed until it's done
```

Each line starts with its time and the replica it came from. Times are in UTC. `pyo logs -f` keeps one stream open to the cluster, and opens it again if it drops.

## Run a command

```bash
pyo exec                                  # a shell
pyo exec -- bin/rails db:migrate          # one command
pyo exec -- sh -c 'echo $DATABASE_URL'    # through a shell
pyo exec -- pg_dump app > app.sql         # output to a file
cat seed.sql | pyo exec -- psql app       # input from a pipe
```

Everything after `--` runs as it is, in a running replica, and `pyo exec` exits with its exit code, so scripts can check it. It runs without a shell, so use `sh -c` for pipes or variables. A command gets a terminal when you run it from one, else its output and errors stay apart and piped input goes to it. `-t` always gives it a terminal, `-T` never does, and `-i` sends what you type without one. `--replica` picks the replica.

Running a command needs the Developer role, and an API key with deploy or full access. A shell needs full access.

## Variables to a .env file

```bash
pyo env pull                   # write the variables to .env
pyo env pull --file .env.prod  # or another file
pyo env pull --secrets         # with the secrets' values
```

It won't overwrite a file unless you pass `--force`. Secrets are written with an empty value and a comment, unless you pass `--secrets`. Only team owners and admins can pull secrets' values, and each one is logged like when it's revealed on the dashboard. The file is readable only by you.

## Volumes

```bash
pyo volume list                          # your teams' volumes
pyo volume snapshots shop/web-data       # its backups, newest first
pyo volume restore shop/web-data         # pick a backup and restore it
pyo volume delete-backup shop/web-data   # pick a backup and delete it
pyo volume resize shop/web-data 50       # grow it to 50 GB
pyo volume attach web-data -s blog/api   # attach it, moving it to blog if needed
```

`pyo volume restore` stops the volume's service, restores the backup and starts the service again. It waits until the restore is done, and so does `pyo volume attach` when it moves a volume. Add `--detach` to not wait. Team owners and admins can restore, delete backups and resize.

## Variables from a .env file

```bash
pyo env push                     # set the variables in .env
pyo env push .env.production --secret STRIPE_KEY
pyo env push --dry-run           # see what would change
```

New keys are saved as variables. Pass `--secret KEY` to save one as a secret, or `--secrets` for all of them. A secret you overwrite stays a secret. For keys that are already set, it asks you on a terminal. In CI, pass `--overwrite` or `--skip-existing`. Changes apply on the next deploy, or add `--deploy` to deploy now.

## Domains

```bash
pyo domain list                      # domains, their status and HTTPS
pyo domain add shop.example.com      # prints the DNS record to create
pyo domain add --free                # a free nip.io domain, no DNS needed
pyo domain add shop.example.com --wait
pyo domain remove shop.example.com
```

Domains apply right away, without a redeploy. `--wait` waits until the domain is live.

## Backups

```bash
pyo backup now                     # the service's volume
pyo backup now --volume shop/web-data --wait
pyo backup now --db cache          # a KV database, or one added under Backups
```

Backups go to the team's backup destination, set up under **Backups** on the dashboard. `--wait` follows the backup and prints its size and time.

## Import from another platform

```bash
pyo import coolify --from https://coolify.example.com --source-token <token>
```

It shows what each project, service and database becomes, then asks before it imports. Use `dokploy` for Dokploy. See [Importing from another platform](/docs/import-platforms).

## Upgrade

```bash
pyo upgrade
```

This replaces `pyo` with the latest release for your system, after checking its checksum. It says when you already have the latest. Add `--version 0.3.0` for a particular release. If you can't write to the folder `pyo` is in, run it as a user who can, or install it again into a folder of yours.

Once a day, the CLI looks for a new release. When there is one, it says so after a command:

```text
Pyo CLI 0.3.0 is out (you have 0.2.5). Run pyo upgrade.
```

It looks in the background, so commands never wait for it, and it stays quiet when you're offline. It doesn't look in CI, when its output isn't a terminal, or when `PYO_NO_UPDATE_CHECK=1` is set.

The CLI can be newer than your Pyo. When it is a minor version or more ahead, `pyo login` and `pyo link` say so, since newer commands may not work until you update Pyo under **Settings › Updates**.

See every command in the [command reference](/docs/cli/commands).
